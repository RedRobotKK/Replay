# DeepSeek findings, 2026-09-28

440 live calls, $0.05 observed balance movement. Every claim below carries its
class. Raw per-trial rows are preserved outside the repository; aggregates only
here.

## F1. Reasoning is on by default, and disabling it is a measured improvement

`deepseek-flash` emits a `thinking` block on the Anthropic-compatible path
unless told not to. **OBSERVED**: at `max_tokens=24` the entire budget went to
reasoning and the response text was empty, with `stop_reason=max_tokens`.

`{"thinking":{"type":"disabled"}}` suppresses it. n=20 per cell, outcome checked
by exact match:

| task | thinking | pass | output tokens | derived USD | wall ms |
|---|---|---|---:|---:|---:|
| extraction | on | 20/20 | 54 | 0.0004943 | 1320 |
| extraction | **off** | **20/20** | **2** | **0.0004591** | **1168** |
| ordering | on | 20/20 | 58 | 0.0002695 | 1286 |
| ordering | **off** | **20/20** | **13** | **0.0002387** | **1042** |
| counting | on | **9/20** | 200 (capped) | 0.0003847 | 2020 |
| counting | **off** | **18/20** | **1** | **0.0002613** | **1147** |

**MEASURED IMPROVEMENT** on extraction and ordering: cost down 7% and 11%,
latency down, pass rate unchanged at 20/20.

Counting is the interesting cell. With reasoning on it passed 9/20 and hit the
200-token cap; with reasoning off it passed 18/20 on one output token. The
accuracy difference is **confounded with the cap**: a run that exhausts its
budget produces no answer and scores as a failure. Whether reasoning would help
counting given a larger budget is `NOT_MEASURED`.

## F2. `reasoning: {effort: ...}` is accepted and silently ignored

**OBSERVED**: `{"reasoning":{"effort":"none"}}` returned 200 with a thinking
block and 59 output tokens, identical to the default. The parameter is not
rejected and has no effect. Anything reading it as a working control would
report a configuration that never applied.

## F3. Prefix ordering only helps when the prefix recurs

The earlier n=4 result reported a 98.3% fresh-token reduction from moving a
static block ahead of the variable question. That measurement was taken with a
**fixed** static block shared by every trial. Re-run with a unique block per
trial, the effect vanishes entirely.

Direct interaction test, n=20 per cell, identical task, outcome checked:

| order | static block | fresh | cache read | derived USD | pass |
|---|---|---:|---:|---:|---|
| static first | unique per trial | 3048 | 0 | 0.0004578 | 20/20 |
| variable first | unique per trial | 3048 | 0 | 0.0004578 | 20/20 |
| **static first** | **shared** | **233** | **2816** | **0.0000440** | **20/20** |
| variable first | shared | 3049 | 0 | 0.0004579 | 20/20 |

**MEASURED IMPROVEMENT, conditional: 90.4% lower cost with outcome preserved,
and only in the shared-prefix cell.** With a unique prefix the two orders cost
the same to seven decimal places.

The recommendation therefore carries a condition:

> Move the stable block ahead of variable content **when that block recurs across
> requests**. When it does not recur, ordering changes nothing.

Stated without the condition it is not a general optimization. The original
98.3% figure was not wrong; it was reported without the circumstance that
produced it, which would have made it a bad recommendation.

## F4. Derived cost over-states observed spend by about 3x

**OBSERVED**: balance moved from $46.89 to $46.84 across the campaign, a delta
of **$0.05**.
**DERIVED**: $0.1458 over the same 440 calls, from the published off-peak table.

The derived figure is **2.9x the observed one**. Peak rates would make it worse,
so the direction is not a peak/off-peak mix-up. Candidate explanations, none
tested: billing lag behind the balance endpoint; rounding at the cent; a rate
that differs from the published table; or an error in the derivation.

This is unresolved and is the reason no DeepSeek dollar figure should ship yet.
A 3x over-statement in a cost tool is worse than no figure.

## F5. Concurrency

**OBSERVED**: 64 parallel requests all returned 200 and median latency fell from
662 ms at 4 concurrent to 575 ms at 64. No throttling was reached. The ceiling is
`NOT_MEASURED` above 64, and no rate-limit headers exist to read one from.

## Corrections to earlier work in this branch

- The 98.3% prefix-ordering figure is **conditional**, not general. See F3.
- A first version of the benchmark tasks seeded the filler text with a constant,
  so every trial shared one static block. It cached in both arms and hid the
  ordering effect completely, showing identical cache reads for both orders.
  Fixed by seeding per trial.
- A first run scored 0/20 on every arm. The cause was `max_tokens=24` being
  consumed entirely by reasoning, not model failure. A uniform zero across all
  conditions is an instrument failure, and was treated as one.
