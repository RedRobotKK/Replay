# Baseline: how much of Replay's own advice can Replay verify?

**Experiment** `verifier-coverage` · **Surface** Claude Code transcripts ·
**Date** 2026-09-28 · **Stage** Baseline (no intervention applied)

## Question

Replay produces optimization suggestions and can mark them applied, then
verified against later sessions. Before optimizing anything, what fraction of
its own output is even eligible for that loop?

## Method

Binary built from `feat/perf-contract` at `a9dea3f`. Two commands, read-only,
against the operator's Claude Code transcript tree.

```
replay cost --json
replay advise -out <scratch> ~/.claude/projects
```

The advice file was written to a scratch path, not to `~/.replay/advice.json`,
so the operator's existing applied/dismissed state was left untouched.

## Result: verifier coverage is 7.8% (OBSERVED)

256 suggestions were produced.

| class | n | share | predicted USD |
|---|---:|---:|---:|
| verifiable (`pending`) | 20 | **7.8%** | 710.70 |
| `advice only` | 236 | **92.2%** | 353.43 |

By kind:

| kind | n | verifiable |
|---|---:|---|
| `hot-file` | 235 | no, `AdviceOnly` by construction |
| `large-results` | 16 | yes |
| `tool-inputs` | 3 | yes |
| `cache-breaks` | 1 | no, `AdviceOnly` by construction |
| `first-turn-content` | 1 | yes |

**One kind, `hot-file`, is 91.8% of all output, and it is one of the two kinds
`advisor.track()` returns `AdviceOnly` for.** The loop's coverage is therefore
not limited by the verifier's logic but by the distribution of what the advisor
finds.

## Second observation: the loop has never completed a cycle here

All 20 verifiable suggestions are `pending`. Zero `applied`, zero `verified`,
zero `not verified`. On this corpus the Find → Recommend → Change → Verify loop
has produced findings and recommendations and has never recorded an
intervention.

This is a statement about the corpus, not about whether the advice is correct.

## What this does NOT establish

- **The $1,064.13 predicted total is a counterfactual, not a measured saving.**
  252 of 256 suggestions carry `estimated: true`, meaning the token figure came
  from the byte-to-token fit rather than from provider-reported usage.
- **No causal claim.** Nothing was applied, so nothing was verified.
- Whether the advice would help if applied: `NOT_MEASURED`.
- Whether `hot-file` suggestions are useful despite being unverifiable:
  `NOT_MEASURED`. Unverifiable is not the same as wrong.

## Recorded for checking, not claimed

Verifiable predicted spend ($710.70) and corpus re-billed spend ($710.15) differ
by $0.55. These are computed by different paths and the closeness may be
coincidence. It is recorded so that a later run can test whether the two track
each other; no relationship is asserted here.

## Next action

The bottleneck is measured and it is the kind distribution, not the verifier.
The next bounded question is whether `hot-file` can be made verifiable, or
whether the advisor's mix should shift toward kinds that can be. Both are
product decisions that now have a number attached.
